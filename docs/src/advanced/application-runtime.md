# Application Runtime

`caelix` provides `Application` for production and `TestApplication` for
in-process HTTP tests on both the Actix and Axum backends (see
[Testing](../recipes/testing.md)). The Axum adapter is documented in [Axum and
Tower](axum.md).

```rust
use caelix::Application;

Application::new::<AppModule>()
    .await
    ?
    .listen("127.0.0.1:8080")
    .await
```

`Application::new` returns startup failures as `caelix::Result<Application>`.

```rust
let app = Application::new::<AppModule>().await?;
app.listen("127.0.0.1:8080").await?;
```

Startup builds the container from module metadata, logs controller routes, runs bootstrap hooks, and stores the adapter route registration function.

Production applications can resolve a registered provider before constructing
native middleware:

```rust
let app = Application::new::<AppModule>().await?;
let audit = app.resolve::<AuditService>()?;
```

## Body Limits and Upload Storage

The default JSON body limit is 1 MiB. Override it before `listen`:

```rust
Application::new::<AppModule>()
    .await
    ?
    .body_limit(2 * 1024 * 1024)
    .listen("127.0.0.1:8080")
    .await
```

The same limit applies to multipart controller routes. Oversized JSON or
multipart bodies return `413 Payload Too Large`; malformed JSON or multipart
data returns `400 Bad Request`. Configure the isolated directory used to stage
multipart file parts with `upload_temp_dir`:

```rust
Application::new::<AppModule>()
    .await?
    .body_limit(10 * 1024 * 1024)
    .upload_temp_dir("/var/tmp/my-service/uploads")
    .listen("127.0.0.1:8080")
    .await?;
```

See [Multipart Uploads](multipart-uploads.md) for route-level upload limits,
file ownership, and typed form binding.

## Workers

`Application` starts the Actix server with one worker by default. Increase it before `listen` when the process should run multiple Actix workers:

```rust
Application::new::<AppModule>()
    .await
    ?
    .workers(4)
    .listen("127.0.0.1:8080")
    .await
```

## Logging

The runtime logs startup, route mapping, listening, and shutdown. Application
logging, levels, Actix access formats, buffering, and Axum differences are
covered in the dedicated [Logging](logging.md) guide.

## Shutdown

`Application::listen` runs provider `on_shutdown` hooks after the Actix server exits. If binding the socket fails after startup has completed, shutdown hooks are also attempted before returning the bind error.

```rust
Application::new::<AppModule>()
    .await
    ?
    .listen("0.0.0.0:8080")
    .await
```

Shutdown hook errors are converted into `std::io::Error` after the server stops.

## Actix Adapter Behavior

The adapter installs:

- Shared `Arc<Container>` application data.
- Shared request configuration with the Caelix body limit, normalized JSON and multipart errors, typed multipart DTO binding, temporary upload storage, and JSON body parsing for `#[body]` routes even when the client omits the `Content-Type` header.
- Generated controller routes from module metadata.
- A request logging wrapper, enabled only when access logging is explicitly requested.

Controller route wrappers are generated by `#[controller]`. Plain routes call the controller directly. Routes that use guards, interceptors, or `#[user]` build a `RequestContext`, run guards, run interceptors, call the controller method, convert the result to a Caelix response, then convert it to `actix_web::HttpResponse`.

### Native Actix middleware

`listen_with_app` accepts an Actix application factory. Actix invokes the
factory for every worker, and Caelix adds its controllers, gateways, OpenAPI
routes, body configuration, fallback, and access logging to the returned app.
Actix Web is available as `caelix::actix_web`, so the middleware always uses
the adapter's compatible version.

This example accepts an incoming request ID or generates one and returns it on
the response:

```rust
use caelix::{
    Application,
    actix_web::{
        App, Error,
        body::MessageBody,
        dev::{ServiceRequest, ServiceResponse},
        http::header::{HeaderName, HeaderValue},
        middleware::{self, Next},
    },
};
use uuid::Uuid;

async fn request_id(
    request: ServiceRequest,
    next: Next<impl MessageBody>,
) -> Result<ServiceResponse<impl MessageBody>, Error> {
    let request_id = request
        .headers()
        .get("x-request-id")
        .cloned()
        .unwrap_or_else(|| {
            HeaderValue::from_str(&Uuid::new_v4().to_string())
                .expect("a UUID is a valid header value")
        });
    let mut response = next.call(request).await?;
    response
        .headers_mut()
        .insert(HeaderName::from_static("x-request-id"), request_id);
    Ok(response)
}

Application::new::<AppModule>()
    .await?
    .listen_with_app("127.0.0.1:8080", || {
        App::new().wrap(middleware::from_fn(request_id))
    })
    .await?;
```

The application using this example adds `uuid` with its `v4` feature. Native
middleware wraps controller responses, framework-generated errors, OpenAPI
routes, and the fallback. Caelix interceptors remain appropriate for
controller-specific behavior but do not replace application-wide middleware.
